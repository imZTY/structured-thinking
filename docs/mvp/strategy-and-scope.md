# 战略与 MVP 范围（v0.2 · 公式推导模型）

> 本文件是产品战略的一页纸快照。决策以"用户确认"为准，修订历史记录在文末。
> 本文回答三问：为什么做（战略）／MVP 做什么（范围）／明确不做什么（边界）。
> 2026-10-25 起产品形态由"思维导图 / 层级有向图"转为"公式推导"，详见文末决策记录。

## 一、战略方向（U 型曲线思维）

结构化思维产品的价值链与本项目在各环节的定位：

```
价值 ───────────────────────────────────────────►
  上游：标准         中游：渲染           下游：内容生态
  内容 JSON 标准      web 渲染框架          topics 内容库
  (语法制定者)        (参考实现)            (复利资产)
  ▲ 高壁垒/高价值     ▼ 商品化/低壁垒        ▲ 复利/高价值
```

**定位一句话：不是"又一个思维导图工具"，而是"结构化思维内容的交换标准 + 内容库，附带一个刚好够用的参考渲染器"。**

### 三条战略纪律（由定位导出，约束一切后续决策）

1. **上游慷慨**：内容标准的工效学（可手写、可校验、可版本化、AI 可生成）是核心投入方向。
2. **中游克制**：渲染器永不参与功能竞赛——与 XMind/markmap 等成熟工具比功能是战略错误。技术形态：零 UI 框架、近零依赖、纯静态部署、近零维护。
3. **下游养生态**：贡献路径（模板 → validate → PR → CI）是产品功能，不是文档附件；内容库的质量复利是长期资产。

### 时代性押注（差异化来源）

结构化内容的生产方式正在从"人手写大纲"迁移到 **"AI 生成 + 人审校沉淀"**。
内容标准的核心隐性生态位：**成为 AI 结构化输出的目标格式**——一段 prompt 即产出合法 `topic.json`。
由此推论：单文件自包含、开放类型词汇、宽容未知字段，这些不是妥协而是战略。

### 商业化路径（长线，非 MVP 范围）

产品若足够好，具备变现潜力；**长远需要一个服务后端**。演进路线：

```
v1 静态单机（GitHub Pages 只读 + 本地 dev 服务可写回）
 └► v2 私有内容（本地 JSON 目录挂载 / 浏览器导入）
     └► v3 服务端（账号、云端内容库、协作、付费场景）
```

关键架构约束：数据层必须是 **"换源不换标准"**——来源从静态文件换成 API 时，标准与渲染层零改动。`core/source.ts` 的 `ContentSource` 接口（读 + `canEdit` / `saveTopic` / `createTopic`）就是这条演进接口。

## 二、MVP 业务建模

### 核心认识：认知框架 = 公式拆公式

顶层是一条大公式，公式里的每个词又可以拆成它自己的子公式，层层向下。这就是认知层的全部。执行层（抓手、方法、想法）是另一件事，必须与认知层分开，不然内容会混在一起。

两种模式把它们隔开，并与白天 / 黑夜主题合一，画面本身就是模式提示：

| | 认知模式（白天） | 行动模式（黑夜） |
|---|---|---|
| 公式 | 可展开、可编辑 | 只读，作为坐标 |
| 说明字段（question / note / details） | 可编辑 | 只读 |
| 行动（actions） | **完全隐藏** | 往词上挂抓手 / 想法 |

代价：暗色主题不能单独用于认知。取舍理由：先想清楚再谈办法，是结构化思维里最容易被破坏的纪律。

### 角色

| 角色 | 描述 | v1 状态 |
|---|---|---|
| 阅读者 | 打开网页，浏览、展开、分享 | 线上只读 |
| 作者 | 本地 `npm run dev`，在页面里直接写公式、挂行动，改动自动写回 `content/` | 唯一能编辑的人 |
| 贡献者 | 手写或 AI 生成 `topic.json` 提 PR | 通过 CI 门禁保障质量 |

### 领域对象

| 对象 | 说明 | 存放 |
|---|---|---|
| Standard | 内容标准主版本（当前 1）与公式文法 | `schema/` + `docs/mvp/content-standard.md` |
| Manifest | 主题清单与顺序（= tab 顺序） | `content/manifest.json` |
| Topic | 一棵词树 + 主题级元数据 | `content/topics/<id>/topic.json` |
| Term 节点 | 公式里的一个词；有 `expr` = 被展开成了自己的公式；`terms` 以词为键 | Topic 内 |
| Action | 挂在词上的抓手 / 想法（`kind` 开放词汇，`status` 可选） | Term 节点的 `actions` |
| ViewState | 展开集 + 选中词 + 模式（派生态，不入库） | 内存 + hash 路由 |

### MVP 用例

| # | 用例 | 验收要点 |
|---|---|---|
| UC1 | 主题切换与新建 | 左下 tab 切换，懒加载，URL 反映当前主题；dev 下 `＋` 新建 |
| UC2 | 公式推导 | 点词展开，子公式铺在父公式正下方；再点收起；层级不限；展开到 2 / 3 / 全部 / 收起 |
| UC3 | 写公式 | 点没有公式的词直接开始写右边；✎ 改已有公式；改名保住子树；非法公式拒绝并保留草稿 |
| UC4 | 检查器 | 选中词后右侧显示面包屑、本质问题、说明、详情、关联、参考；认知模式可编辑 |
| UC5 | 行动层 | 行动模式下往词上添加 / 改 / 删抓手与想法，抓手有 待办→进行中→完成 状态 |
| UC6 | 撤销重做与自动保存 | ⌘Z / ⇧⌘Z；改动 500ms 内写回；关页前补写 |
| UC7 | 深链 | `#/topicId/词/词…`，刷新与前进后退保持，祖先公式自动展开 |
| UC8 | 内容贡献 | 模板 + `npm run validate` + CI 门禁 |

## 三、MVP 功能点范围

### F1 推导式视图（读旅程的地基）

- F1.1 公式自上而下堆叠；展开的子公式缩进并带左侧细线，一眼看出层级
- F1.2 词的下划线语义：粗实线 = 已展开；点线 = 有公式但收起；无线 = 还没有公式
- F1.3 运算符按文本流排版（＋ − × ÷ 括号），浏览器原生换行，窄屏可用
- F1.4 行动模式下词旁显示行动条数

### F2 公式文法与编辑（标准的核心）

- F2.1 一条公式 = 一行纯文本 `左边 = 右边`；右边按运算符切词，每个词自动成为锚点；`[...]` 手动成词；数字不成词
- F2.2 不做富文本编辑器：纯文本加解析在中文输入法下更稳，也与 JSON 里的 `expr` 字符串同构
- F2.3 子公式的左边必须等于它在父公式里的词；改名自动带走子树，删词会提示丢弃了多少下层
- F2.4 同名的词各自独立，保持树结构，不做跨公式共享

### F3 主题 tab 系统

- F3.1 左下角 Excel-sheet 式 tab 条
- F3.2 tab 顺序 = manifest 数组顺序；主题懒加载
- F3.3 dev 下 `＋` 新建主题：服务端生成 id、登记 manifest、直接进入根公式编辑

### F4 检查器（卡片轻、面板重）

- F4.1 未选中时显示主题概述；选中后显示该词的面包屑、公式、认知字段
- F4.2 `links` 渲染为 chip，点击跳转并展开祖先；`refs` 渲染为外链
- F4.3 窄屏下检查器移到底部

### F5 路由与分享

- F5.1 hash 路由 `#/topicId/词1/词2…`，每段 `encodeURIComponent`
- F5.2 非法路径降级到最长合法前缀

### F6 写回与贡献链

- F6.1 dev 服务提供 `PUT /api/topics/:id`、`POST /api/topics`：写入前走与 `npm run validate` 同一个校验模块，非法内容到不了磁盘；先写临时文件再 rename；拒绝跨站请求
- F6.2 生产构建没有这些接口，页面自动只读
- F6.3 `content/topics/_template/` 可复制骨架；`npm run validate`；CI 拦截

## 四、明确不做（v1 边界）

- ❌ 富文本公式编辑器（见 F2.2）
- ❌ 协同、账号、评论、线上写回（进 v2/v3 演进线）
- ❌ 同名词跨公式共享（要引入图结构，等有真实需求再议）
- ❌ 在公式之外画图：连线、层内有向边、画布平移缩放（旧图模型已取代，见决策记录）
- ❌ 多文件分片、渲染器插件系统、主题皮肤
- ❌ 种子内容的正式转换——验收后再做；当前两个主题是验证标准用的 demo

## 五、技术选型清单

### 架构总纲：纯核架构（跨端战略的落地形态）

```
content/*.json  ──标准──►  web/src/core/  ──纯逻辑、零 DOM──►  web/src/ui/  ──薄适配层──►  浏览器/PWA
schema/formula.mjs ───────────┘（公式文法唯一实现，校验器与渲染器共用）
```

跨端路线：**标准即跨端资产**。不引入 React Native/Flutter 等多端框架；PWA 先行，真需上商店时用 Capacitor 将现有 web 构建包壳；极端情况下 `core/` 纯 TS 可整体移植。

## 待决：终局愿景如何落到新模型上

2026-10-24 的终局愿景（多层有向图、3D 渲染、一键转架构图）建立在旧图模型上。新模型是一棵公式词树，标准里仍不含任何渲染坐标，所以仍可投影成图、3D 或架构图；但旧模型里的**层内有向边（含反馈环）已在迁移时折进了对应节点的 `details`**，新模型暂时没有结构化表达"反馈 / 先后"的位置。

这条未与用户确认，先记在此处。等用户给出新的终局判断后，再按"由果溯因"纪律决定是否给词之间加关系边。
