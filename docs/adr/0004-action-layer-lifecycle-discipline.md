# ADR-0004: 行动层（actions/ideas）的生命周期清算纪律

- Status: Accepted
- Date: 2026-10-27
- Deciders: zengtianyi
- Related: ADR-0003

## Context

认知框架的行动层（`actions`: `kind: action/idea`、`status: todo/doing/done`）在框架经历过一次真实执行（访谈）后面临清算问题：访谈提纲类的 actions 已执行完，散落各节点的「问主编」类 actions 有的拿到答案、有的没执行到，访谈又产出了一批新待办。若不做清算，行动层会退化成「历史遗迹堆」——使用者分不清哪些还活着。

## Decision

框架每经历一次真实执行（访谈、里程碑、复盘），对行动层做一次三向清算：

1. **已执行 / 已获答案 → 标 `done`，且必须在 text 里如实记录执行情况**——部分执行就写「部分执行：拿到了什么、什么没执行到」。答案本身回注认知层（note/details），行动层只留完成态记录。
2. **未执行到 → 保留 `todo`，text 注明「何时问过、缺什么」**——同时它们自动构成下一次访谈的议程。
3. **新待办 → 按「归属」而非「时间」挂载**：挂在行动所服务的那个公式元素上（如「启动视频号」挂 `自有触达`、「专栏规划」挂 `写作履历`），跨阶段的放在根节点。拒绝按时间线把待办堆在根节点。

配套规则：
- **诚实性高于整洁性**：提纲里约一半的数字类问题被流量话题挤掉没执行到，这些 done 记录如实写「未问到」，不粉饰为完成。
- **idea → action 升格**：idea 是「待判断的想法」，一旦被业内判断验证（拿到机制解释或优先级判定，如「当务之急」），升格为 action 并在 text 注明依据。
- action 对象字段封闭（`kind/text/status`），访谈时间戳等元信息只能写进 text，不能加字段。

## Options Considered

1. **删掉已执行的 actions 保持树干净** —— 否决：done 记录本身就是「框架被真实使用过」的证据链，且部分执行的情况记录直接生成下次访谈议程；删除等于丢日志。
2. **全部保留原样不清算** —— 否决：todo 与 done 混杂，使用者无法区分活待办与遗迹，行动层失去运营价值。
3. **三向清算纪律** —— 选用：done 留痕、todo 标注缺口、新待办按归属挂载——行动层同时成为「执行日志 + 待办看板 + 下次议程」。

## Consequences

**正面**：
- 行动层始终反映真实状态，活待办一眼可辨。
- 「未执行到」的 todo 与 note 里的「待校准」互相印证，认知层与行动层形成闭环。

**负面**：
- text 里掺入执行注记（括号补充），单条 action 可读性下降、变长。
- 每次执行后需人工走一遍清算，有维护成本。

**风险 / 后续行动**：
- 若未来 done 记录大量累积导致行动层噪音过高，可考虑在内容标准 bump 版本时引入归档机制（如 `archived` 状态或按事件分组），当前规模不需要。

## Good Cases

- 根节点访谈脚本 4 条 → 全部标 done，text 里如实记录：「10–35 分钟…部分执行：版税区间已拿到，保本印数 / 发货折扣 / 竞品实销被流量门槛话题挤掉，未问到」。
- `问主编：出版社对素人的自有流量有没有门槛？` → 标 done，答案（5 万 / 10 万 / 50 万）回注 `自有触达` note。
- `现在就开始把方法论文章公开发布` → idea 升格 action，text 注明「白宇原话：这件事我认为是当务之急」。

## Bad Cases

- 假想反例：把「发公众号给白宇」这类新待办统一堆在根节点按时间排序——阶段推进后根节点变成流水账，且无法从公式元素直接看到「这个词上有什么待办」；正确做法是能归属就归属（本条实际挂在了根节点 actions，因为它是访谈收尾的跨阶段动作，归属判断允许例外但应有意识）。
- 假想反例：未问到的「问主编：保本印数多少」直接标 done 或删除——丢失下次访谈议程；正确做法是保留 todo + text 标注「2026-10-26 未问到，下次访谈补」。
